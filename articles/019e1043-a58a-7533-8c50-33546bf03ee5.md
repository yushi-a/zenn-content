## はじめに
cloudflare tunnelはポート開放が不要でk8sを外部公開できるので個人開発においてとても便利です。
私の環境ではcloudflared podの後ろにIstio IngressGatewayを配置することでクラスタ外部からの受ける部分とクラスタ内部のルーティングを分離しています。（cloudflaredでもhostnameやpathでのルーティングはできますが、Istio IngressGatewayの方が機能が多いため現状この構成にしています）
この構成だとブラウザからcloudflaredまではcloudflare tunnelによりTLS通信が行われています。またIstio IngressGateway以降の部分もistioの機能でmTLSが効いています。しかしcloudflaredからIstio IngressGateway間の通信はhttpになっており暗号化されていない状況です。
今回はこの部分についてもTLS化してみたのでその手順をまとめます。

## 実施手順
今回方針としてはistio管理によるmTLSで実現することにしました。理由としてはクラスタ内通信はIstioでまとめて管理したほうが楽そうかなと思った程度でちゃんと比較検討したわけでは無いです。

### 1.cloudflared podにIstioサイドカーを注入する
まずはcloudflared podがIstioのmTLS通信ができるようにサイドカーを注入します。
私はDeploymentで管理しているので以下のようにします。

```diff
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cloudflared
  labels:
    helm.sh/chart: cloudflared-0.1.0
    app.kubernetes.io/name: cloudflared
    app.kubernetes.io/instance: cloudflared
    app.kubernetes.io/version: "1.16.0"
    app.kubernetes.io/managed-by: Helm
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: cloudflared
      app.kubernetes.io/instance: cloudflared
  template:
    metadata:
      labels:
        app.kubernetes.io/name: cloudflared
        app.kubernetes.io/instance: cloudflared
+        sidecar.istio.io/inject: "true"
    spec:
      ...
```

### 2.DestinationRuleで送信側のmTLSを設定する
cloudflared nsにDestinationRuleを作成し、Istio IngressGateway宛の通信にISTIO_MUTUALを適用する。
hostのistio-ingress.istio-ingress.svc.cluster.localは自身の環境に合わせます。

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: cloudflared
  labels:
    helm.sh/chart: cloudflared-0.1.0
    app.kubernetes.io/name: cloudflared
    app.kubernetes.io/instance: cloudflared
    app.kubernetes.io/version: "1.16.0"
    app.kubernetes.io/managed-by: Helm
spec:
  host: istio-ingress.istio-ingress.svc.cluster.local
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL
```

### 3.Gatewayで受信側のmTLSを設定する
Istio IngressGatewayのGatewayリソースで内部HTTPS通信用ポート（8443）を開けてTLSモードをISTIO_MUTUALに設定します。
hostsは`"*"`にする必要があります。
80番ポートも記載してますが、IstioのmTLSしか許可しない場合は不要です。

```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: cloudflared-gateway
  namespace: istio-ingress
spec:
  selector:
    istio: ingress
  servers:
  - port:
      number: 8443
      name: https-internal
      protocol: HTTPS
    tls:
      mode: ISTIO_MUTUAL
    hosts:
    - "*"
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - "*"
```

### 4.Cloudflare Tunnelの転送先を変更する
手順3で設定したポート宛にルーティングするように変更します。
これはGUI上から設定変更します。
もともと80番ポートになっていたものを8443ポートにするだけです。
注意点としてここではhttpsじゃなくhttpとしています。これは実際にmTLSを担うのはサイドカーのIstio proxyでありcloudflaredアプリ自体はTLSを意識する必要がないからです。もしここでhttpsを指定すると二重TLSになり正常に通信ができなくなります。

```diff
- http://istio-ingress.istio-ingress.svc.cluster.local:80
+ http://istio-ingress.istio-ingress.svc.cluster.local:8443
```

### 実通信のログによる確認
まずはIstioのアクセスログを有効化します。またTLSを確認できるようにフォーマットを以下のように変更しています。

```
"accessLogFormat": "[%START_TIME%] \"%REQ(:METHOD)% %REQ(X-ENVOY-ORIGINAL-PATH?:PATH)% %PROTOCOL%\" %RESPONSE_CODE% downstream_tls=%DOWNSTREAM_TLS_VERSION% downstream_san=\"%DOWNSTREAM_PEER_URI_SAN%\" upstream_tls=%UPSTREAM_TLS_VERSION% upstream_san=\"%UPSTREAM_PEER_URI_SAN%\" \"%REQ(X-FORWARDED-FOR)%\" \"%REQ(:AUTHORITY)%\" \"%UPSTREAM_HOST%\" %DOWNSTREAM_LOCAL_ADDRESS% %REQUESTED_SERVER_NAME%\n",
```

Istio IngressGatewayやcloudflaredのpodを再起動した上で、サイトにアクセスし通信を発生させます。

Step1: Istio IngressGatewayのアクセスログ

```
> kubectl logs -n istio-ingress istio-ingress-69cdbccf7f-qg4kq -c istio-proxy --tail=3
[2026-05-17T08:31:46.302Z] "GET / HTTP/1.1" 200 downstream_tls=TLSv1.3 downstream_san="spiffe://cluster.local/ns/cloudflared/sa/default" upstream_tls=TLSv1.3 upstream_san="spiffe://cluster.local/ns/httpbin/sa/default" "60.103.51.229,10.42.0.1" "httpbin.xxx" "10.42.0.188:80" 10.42.0.204:8443 outbound_.8443_._.istio-ingress.istio-ingress.svc.cluster.local
```

downstream_tls=TLSv1.3、downstream_san="spiffe://cluster.local/ns/cloudflared/sa/default"になっており、cloudflared → istio-ingress間のmTLSが正常に動作していることを確認できます。

Step2: Cloudflared sidecarのアクセスログ

```
❯  kubectl logs -n cloudflared cloudflared-6f5b6958f5-2hgmj -c istio-proxy --tail=5
[2026-05-17T08:31:41.461Z] "- - -" 0 downstream_tls=- downstream_san="-" upstream_tls=TLSv1.3 upstream_san="spiffe://cluster.local/ns/istio-ingress/sa/istio-ingress" "-" "-" "10.42.0.204:8443" 10.43.102.253:8443 -
```

upstream_tls=TLSv1.3、upstream_san="spiffe://cluster.local/ns/istio-ingress/sa/istio-ingress"になっており、istio-ingress宛の通信がmTLSになっていることを確認できます。

### （おまけ）メトリクスから確認
PrometheusのTCP metricsでも確認可能です。
Promethusで以下のようなクエリを実行して`source_principal`と`destination_principal`にspiffeの値が入っていればmTLS通信ができています。mTLSを設定しない状態で試すとunknownになります。


```
istio_tcp_connections_opened_total{source_workload="cloudflared",destination_workload="istio-ingress"}
```
出力ラベル例。
- source_principal="spiffe://cluster.local/ns/cloudflared/sa/default"
- destination_principal="spiffe://cluster.local/ns/istio-ingress/sa/istio-ingress"

connection_security_policyのラベルは本来設定されるようですが、今回はunknownになります。またkiali等で見てもmTLS表記にはなってなかったです。このあたりはちゃんと確認できていないですが、ingressの前段にistio proxyが来るという本来の使い方とは異なる構成になっているためだと思われます。

## まとめ
k8s環境にCloudflare tunnelとIstioを導入した構成で、Cloudflared → Istio IngressGateway間の通信をIstio管理のmTLSによって暗号化しました。
設定値やアクセスログからmTLSが有効になっていることが確認できました。
